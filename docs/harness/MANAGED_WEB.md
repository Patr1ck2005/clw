# CLW 网页主控与协作合同

本说明由开发合同生成公开投影，保留通用工具行为；不携带开发实例的账号、绑定、历史回执或验收记录。实际参数以当前工具合同与原请求为准。

## 协作的日常流程：送任务、带回结果

日常协作应接近手动复制粘贴。M 决定研究方向、任务量、分工、结果取舍和后续修复；CLW 负责把工作包送到正确对话，保存回复、等待子任务，并把完整结果和真实错误带回 M。不要要求模型为了流程推进反复调用 context、wait、result、checkpoint、turn-end；程序不凭研究耗时、措辞或自己的业务判断替 M 改计划。

实现沿用已有 `text_v1`、原任务账本及调度，不新增一套系统。主控结束时只需一个末尾决定块，例如：

```clw-plan-v1
{"version":1,"action":"dispatch","workers":[{"key":"A","objective":"给 A 的完整工作包"},{"key":"B","objective":"给 B 的完整工作包"}]}
```

已有子对话填写原 `target`；新对话可写 `title`。`wait` 和 `resume` 可省略，程序默认等待本批结果，M 也可用 `resume` 留下整合要求。新协作者省略 `access/write_paths` 时沿用父任务在该目录内的已有授权；只读核验显式填 `access=read`，独立写入可声明较小写域，不再重复授予已有权限。已接入的 worker 普通工作回合正常回复即可，不输出管理命令。已保存的长回复从对应原成果文件核验后完整带回，不用界面摘要代替正文；受阻回复连同已完成工作和原错误一起呈现，M 自主判断独立后续工作。部分送达、执行未知和真实拒绝仍如实区分，不包装为成功。正文超过现有单条容量时仍需分批，不能静默截断。

首次接入仍通过真实 Session 执行 `enroll`，与完整首任务共用一条网页消息；当前首次结果仍通过 `turn-end` 交付，不能把普通回合的“无管理命令”推广到首次。`first_task_ready` 和原协议 `context` 直接返回 `result_delivery`：带原 request/claim 的参数和固定操作键、完整 CLI 参数列表及结果格式。模型只填成果，不必为收尾另读管理手册、重复接入或再开状态回合。首任务全文由程序按原请求与结果回执关联后带回，兼容旧结果编号被脱敏的记录。子对话只接收本包工作、真实执行范围与交付说明，不复制主控的建组、等待、检查点及关闭团队教程。管理细节应由程序承担，不能成为独立的模型任务；业务拆分和问题处理仍由模型自主决定。

原任务保留自己的协议、账号和请求身份，不因界面简化自动迁移。原身份、重复发送、用户暂停和未知副作用由程序维护；Codex＋Web 的原生上下文运输保持。

访问权限和写入占用分别核对。已暂停且原任务/运行结束、没有未知发送或执行时，操作员可沿原 scope 的子目录收紧写域；原 Project/Session、账号和实际访问权限保留，不能借此扩大授权。真实父子写域、共享资源和未知 Git 证据继续受现有准入保护，历史成果不因范围调整被接受或重派。

## 每轮正式开发的工作量

委派的 `write_paths` 是相对项目根目录的执行范围，文件或目录都可声明。目录末尾的一个 `/` 或 Windows `\` 会被规范化，不按交付文件引用规则拒绝；绝对路径、穿越和重复等仍返回参数错误。导出产物继续单独遵循产物引用规则，不能把执行范围当成导出许可。

每次正式开发对话承载尽可能充实的重度工作，在同一回合连续完成多批有实质成果的增量。读取、设计、实现、接线、验证、修复与交付一起完成；游戏按当前目标统筹素材、模型、人物、机制、动画框架、场景和内容，研究合并相关推导、计算、证据核验与成稿。关键变化保存后继续，从真实未完处推进，不因耗时或一个增量完成就提前结束，也不为凑工作添加无关任务。

实际运行提示的唯一正文为 [work-package-policy.json](../../config/work-package-policy.json)，接入首任务、普通主控和worker、持续目标下一包及Codex＋Web正式工具回合读取同一内容。仅接入、明确只读准备和上下文压缩保持各自目标；恢复提示保持简短，沿原正式目标继续。安装与人工操作见[使用说明](../../README.md)。

## 持续目标的接续与暂停

2026-10-04追加交互约定：普通暂停、任务切换、移出侧栏、保存补充/goal/验收/额度和设置不打断当前网页工作。默认“暂停自动推进”只停止下一次派发；已送达回合继续接收原工具回执、完成已授权确认、收集并保存结果。界面须同时表达当前回合与后续自动化，不用一个“已暂停”掩盖仍在工作的网页。暂停期间输入框只“保存补充”，单独“恢复自动推进”才允许后续；不因Enter保存文字解除暂停。隐藏任务与物理关闭不同，未知回执保留页面；工作或状态未知时拒绝刷新。普通退出保留未结业务，只在当前网页及原执行者确已空闲后关闭；严格维护退出另须原维护停稳证明，详见[退出合同](APP_CONTROL.md#原退出的核对与接续)。真正“停止网页生成”单列且说明主控/协作者范围，不保证恢复隐藏思考，也不代表本地Job已经终止。Native/本地Codex缺少的中断或可逆暂停能力不伪造，仍沿原终端真实入口。实现及现场装载状态分别读CURRENT。

普通对话正常回复后停止。Goal 默认可自动接续：当前结果返回完整目标的交付状态，全部完成即“已交付”，有必要剩余工作才继续，不增加独立 AI 审查回合。保存目标不立即发送，原暂停保持；可关闭自动接续，保留人工发放后续的旧方式。旧 Goal、账号和结果保持原约定，新规则从明确保存、发送或恢复时生效。运行时长和发送次数默认不限，用户显式预算与平台额度照常处理。

输入框上方用简条显示 Goal 的运行、等待结果、已交付、暂停或需要处理。目标编辑与可选预算集中在同一窗口，自动模式不要求逐包人工验收；旧人工模式仍保留原决定。草稿和模式修改关闭后保留，未知保存核对同一次操作。

目标、验收决定及下一包补充的编辑基准与本机草稿一同保存。未编辑的窗口可同步另一入口保存的新记录；已有编辑遇到目标版本或关联工作包变化则保留当前记录与原稿，明确显示冲突并停止提交。用户核对后才能更新本机编辑基准，不能拿新版本号悄悄覆盖旧稿。已提交但回执未知的操作仍核对原键与原参数，不因记录更新换键提交。

接续前必须核验原结果、原请求和 closed run、完整交付身份以及无未决执行。网页最终回答失败但已保存真实工具总结时，程序可核验同请求的总结、失败、回收回执、目录/字节数/哈希与原浏览器 attempt/user 身份，再按[原Session执行核验](#原-session-的执行核验)核对全部活跃状态、未知结果与原Job；确认执行已结束且当前网页空闲，才准备唯一新请求。查询在事务外完成，预留发送前重新核验原目标与证据；人工验收不冒充所有外部 Job 空闲。精确独立一行 `CLW_GOAL_STATUS: ready_for_review` 只用于旧自动目标停在完整目标人工验收，其余自然语言不代替目标状态。

因额度可能不足、时间安排或希望暂缓而说“先停下来／暂停”时，默认只停止下一工作包的自动续发，让已开始的当前完整工作包继续实施、回收、整合并保存结果。目标接续层记录暂停，不点击网页停止生成，不暂停在途主控/worker，不取消已受理 Job，也不重启工作页面。这样保留已经消耗的模型推理和已完成工作。只有用户明确要求立即中断当前思考/执行时，才使用相应停止入口并保留原记录。后台程序与监督不得自行把额度疑虑扩大为打断正在做的工作。

用户明确恢复后撤回相应目标暂停，先核原请求、执行、成果和已受理/未知操作，沿原任务继续；不因暂停期间的 UI 提示另开任务或重做原命令。真实权限、明确政策限制、独立停止和维护检查点仍按各自合同处理。

旧自动模式的兼容CLI在失败工作包已结清、需要接受新完整工作包时，操作顺序为：先保留目标暂停，以唯一操作键接受同一身份的新请求；再通过带 `expected_request_id` 的正式页面入口明确恢复原页面；确认页面已绑定、未暂停、绑定已启用且没有待处理问题或未恢复停止后，才用 `adopt-request` 将持续目标接到新请求。接续检查本身不发送、不清除问题、不解除停止。重复核对已经接受的同一接续只读取原结果，不替代新的恢复授权。

Web Pro应先充分自行排查、修复并尝试已授权的可行路径。局部阻碍只停住受影响步骤，其余必要开发、验证和整合继续；不能因为旧资源占用、某项验收受阻或一次工具失败而交回整个目标。只有确实无法自行解决且已无必要工作可推进，才以 `needs_attention` 退出并给出原错误、已尝试路径、其他必要工作为何也无法继续及用户需要完成的一步。明确拒绝、真实访问限制、用户停止和未知执行仍保持，不用这条要求绕行。实际提示统一读取 [工作包正文](../../config/work-package-policy.json)，不维护另一份提示模板。

## Codex＋Web 的上下文来源

已对照固定上游 v6.1.1 与 CLW 增量：将 `systemPrompt` 和本次原生请求的 `messages` 编码为网页可见上下文，是上游桥接实现。CLW 的额外适配包括用户授权、工具路线说明和消息来源澄清，未另行抓取主控 Codex 对话的完整历史。独立工作包通过 `codex exec` 启动自己的原生任务；网页收到该工作者的运行说明、适用项目规则、工作包及其执行历史。主控项目背景由主控整理进工作包，只有明确接续原线程才沿其原历史继续。后续同网页保留增量消息接续。

保留原生工具消息及任务身份；固定系统说明在同一已完成的原网页回合后复用，正常接续只发送增量上下文。未知、失败或新线程仍提供完整必要说明。工作包给足目标、证据入口和验收条件，不无差别搬运主控历史。

## 网页主控的工具

所有本地命令均通过本对话已经授权的 Local-MCP 工具执行，不由浏览器直接执行。
同步调用可以直接返回结果；长时间或后台执行若产生 Job，必须沿原 Job ID 核对，不能伪造 Job 身份。
下面的管理 CLI 位于本安装根 `scripts/`；工作文件仍使用实际项目的授权根。

```text
python -X utf8 -B <安装根>/scripts/harness_managed_client.py context
  --store-id <本次实际store> --target <本对话target> --session-id <自己的Session>
```

`context` 返回原始 request、claim 和运行窗口。初次目标发送确认后，程序自动建立 run，
无需重复 `open`。新的普通工作包默认不限制运行时长或发送次数；旧任务原显式预算保留，用户可按需设置。
worker 数量无固定上限；原 `max_parallel=0` 表示不按人数限流，旧调用可显式设置自愿预算。
新 worker 的接入发送也计入当前 run；工具等待、页面检查不调用模型。

`create` 创建真实独立页面。未指定 `model` / `effort` 时继承主控；主控可以为每个 worker 分别指定模型和思考档位：

```json
{"title":"完整独立工作块","root":"绝对且已授权的现有工作目录","effort":"中","access":"read","write_paths":[],"resources":[],"first_turn_instructions":"读取指定交接，完成本工作块的独立核验与完整结果；列出证据和未决项。"}
```

```text
python -X utf8 -B <安装根>/scripts/harness_managed_client.py create
  --store-id <实际store> --target <本对话target> --session-id <自己的Session>
  --operation-id <固定操作键> --payload-json <上述JSON作为单一参数>
```

例如同一极高主控可以创建 `effort:"中"` 与 `effort:"极高"` 的两个协作者；不是所有子对话强制同档。
支持当前账号/模型网页真实提供的任何档位，不根据写死的档位序号猜选项。
`Medium` / `Extra High` 等常用英文写法也可用。若明确指定 `model`，使用网页实际模型名称；不自动切换提供方。
程序在 worker 首次接入发送前读取公开菜单和可用性、选择并再次核对，把实际模型/档位保存到该 worker。
不存在或锁定的选项会报告 `model_unavailable` 并唤醒等待中的主控，不用其他档位冒充。
`context.worker_configuration` 提供新合同，`pages` 和侧栏分别显示每个 worker 的实际档位。

返回 worker target 后，用 `wait-ready` 和固定 `--operation-id` 等待接入。
`--payload-json` 为 `{"targets":["返回的target1","返回的target2"]}`。
返回 `waiting_events` 后立即结束本轮网页回答；程序在页面全部就绪或出现明确故障时合并事件，
自动唤醒原 request/claim。`context.waiting_pages` 给出就绪与失败信息。不要让模型循环检查。
旧 `wait-pages` 作为兼容命令保留：是有界后台 Job，默认 1800 秒，未知回包只能查原 Job。

页面就绪后，沿用 `harness_team_client.py` 的
`assign / wait / result / checkpoint / pause / resume / close`。
具体字段查 CLI 的 `--help` 与本次工具返回的真实合同；身份必须来自本次 context。
先分配独立工作目录/worktree 和 Git、Unity 等排他资源，再 assign；同一写根串行。
不要为同一任务创建新的 run 或换 claim。

常用 team payload（命令行同样带实际 store/target/本人 Session；写操作带固定 operation-id）：

```json
{"run_id":"实际run","after_seq":0,"work_after":0,"snapshots_after":0}
```

上面用于 `context`。`assign` 使用 `run_id, claim_id, target, text, depends_on, resources`。
`result` 使用 `run_id, request_id`，分页追加 `after_seq`。
`checkpoint` 使用 `run_id, expected_version, summary, references, basis_seq`；版本属于当前真实线程，
后继的首次 checkpoint 为 expected_version=0，不把前任的版本当成自己的版本。
`close` 的字段只有以下四个，不加 version/status/confirm 等字段：

```json
{"run_id":"实际run","claim_id":"当前本人的claim","summary":"完整结果与限制","references":["成果文件引用"]}
```

close 返回 `closed` 才是 run 已关闭；随后 managed `turn-end` 保存完整结果、outcome=completed。
明确字段拒绝表示未执行，可以读合同后更正；unknown 或 accepted 则只核原回执，不能换键重放。

`pages` 每页 128 项，沿 `next_after` 取完。team `context` 的信号、任务和快照分别使用
`after_seq`、`work_after`、`snapshots_after`；各自检查 `has_more`、`work_has_more`、
`snapshots_has_more`。分页只限制一次返回的大小，不限制并行 worker 数量。

`wait` 返回 `waiting_events` 后结束网页回答。网页结束与业务任务完成分开记账；
worker 结果到达后程序继续原 request/claim。提前到达的结果应在本轮读取，重复事件不再唤醒。
完整读取所有相关 result 后 checkpoint/close，并提交最终公开结果。

worker 的公开回合 `needs_attention` 也会唤醒等待全部结果的主控；与已经到达的成果合并处理，
不会自动恢复受阻 worker。`team context/result` 返回 `attention` 和完整 `artifacts`，
仍保留原请求、claim 和受阻状态，不把保存的草稿算作任务完成。平台拒绝不重试或绕过。
主控在本轮统一读取、整合和安排后续，不为例行管理单独增加网页回合。

主控读完受阻分支的 `team result` 和完整稿件后，如果确认不必继续该分支，可以在同一回合
调用 `team settle-attention`，字段为 `run_id, claim_id, request_id, attempt_id, reason`。
其中 claim_id 是主控自己的 claim，request_id/attempt_id 是受阻分支在 result.attention 中的真实身份。
它只允许已结束并暂停、无独占资源和未读补充的只读分支；保留原稿与原 claim，明确记为 blocked，
不会写入作者成功回执或重试被拒调用。若该页只是本回合的系统暂停，返回 worker_available_for_new_work=true，解除空闲页面暂停；主控可在当前回合 assign 有效的新工作，并在任务中合并旧成果及恢复说明。旧请求仍为 blocked，不重放，也不单独发“继续”。用户暂停/停止、其他告警和无法证明归属的旧暂停均保留。之后主控可按实际结论整合并 close。写入／独占资源／未知执行仍须先核对。
这是一项明确的分支收束决定，不是将未完成任务自动判为完成，也不评价数学结论。

worker 完成或需要人工处理时，结束网页回答前调用 managed CLI `turn-end`，带固定
operation-id 与 `{"request_id":"原request","claim_id":"原claim","outcome":"completed",
"markdown_path":"工作根内的相对结果文件.md"}`。也可使用 `markdown` 提交不超过 48000 字符
的原始内容，二者只选一个。需要处理时 outcome 为 `needs_attention`，原任务和 claim 保留。
`wait` 已让出时程序自动记为 yielded；无需额外声明完成。

无需在每次收尾前再例行调用 `context`。`turn-end completed` 会在同一事务核对新补充：
返回 `additional_instructions_pending` 时，本次结果尚未保存，请在当前网页回合处理返回的要求，
再以新的 operation-id 提交更新后的完整结果；`has_more` 表示还有未读补充。只有实际返回的要求被标记已读。
回包未知先用原 operation-id 查原回执；不会因重试而丢失补充。`needs_attention` 仍可直接保存已有成果，
不强制重试已被拒绝的读取。主控 `close` 如提示未读补充，在当前回合读取处理后再收尾。

长 Markdown 的 JSON 用 `--payload-stdin` 输入，避免单个命令参数长度限制。
256 KiB 是完整 JSON 的 UTF-8 传输字节上限；其中 `markdown` 字段仍最多 48000 字符，两个上限同时生效。
与 `--payload-json`、`--payload-file` 互斥。只读 worker 也能从 stdin 提交完整结果，不需要
为回复创建项目文件或扩大写权限；Windows 输入须为 UTF-8。原 operation-id 始终不变。

## 安全交接到后继对话

仅在安全点交接：子任务已结束、所有新结果完整读取、追加要求已读、本地 Job 已核对并结束、
没有未知发送。先用 team `checkpoint` 保存公开定义、证据边界、文件引用及未决问题，basis_seq
必须对应当前最新信号。随后 managed `handoff` 使用固定 operation-id：

```json
{"request_id":"原request","claim_id":"原claim","checkpoint_version":1,"no_pending_jobs":true}
```

`no_pending_jobs` 是前任据原 Job 回执作出的明确声明；程序尚不能独立证明所有 Local-MCP Job 静止。
返回后结束本轮。程序看到真实回合结束才接入后继。后继使用自己的 Session/claim，先读取
`context.handoff` 的完整公开检查点；原 run、deadline、发送预算不重置，接入也计入原预算。
已读结果游标沿原记录继承，不伪造为后继已重新阅读。旧 Session/请求/成果保留，只读；可复用
已结束的 worker，不能改写它们的真实归属。交接窗口若用户明确暂停/退出，不会自动开工。

## 结果与恢复

优先通过项目工具保存原始 Markdown、LaTeX、源代码和引用，再在公开回复中给出文件路径。
浏览器补充采集 HTML→Markdown，保留 KaTeX 源、代码语言与围栏、表格、链接；完整采集文件
保存在同一账本目录的 `managed-results`，长结果通过路径与 SHA256 引用，不截断原文件。
已有工具成果和原 Job 是恢复依据，不能把程序重连当作重新执行授权。

代理故障、登录失效、用量限制、模型不匹配和未知发送需要核对；不能自动换账号、模型、
提供方或绕过权限。只有页面明确生成错误时才使用现有有界退避。没有新事件不发“继续”。
界面数字是本地记录，不是官方额度余额。

「暂停自动推进」停止新派发；「停止网页生成」还中断选中主控与其 worker 的网页生成。
两者都不冒充已经终止本地 Job。停止后原 request/claim 保留，明确恢复才继续核对原 Job。
关闭任务或移出侧栏项目保留文件与记录。平台拒绝、用量上限、登录失效不能自动重试或换账号规避。
